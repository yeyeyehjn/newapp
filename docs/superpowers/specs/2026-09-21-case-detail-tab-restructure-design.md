# 案件详情页 Tab 结构重构 · 设计文档

- 日期：2026-09-21
- 范围：`src/components/CaseDetail.tsx`（穗仲云移动端 H5 案件详情）
- 类型：信息架构重组 + 原生保留

## 1. 背景与目标

现状页面为 **7 个顶层 tab**：基本信息 / 当事人 / 仲裁请求 / 证据和质证 / 主要材料 / 文书签名 / 裁决书核阅。

首轮 impeccable crítica 确认关键问题：
- 顶层 7 项 tab 是唯一 >4 的决策点，400px 视口需横向滚动，「文书签名 / 裁决书核阅」近名易混淆（P1）。
- 双语义色系统叠加（`申请人=emerald/被申请人=red` 与 请求段 `indigo/反请求段 amber`），易误读。

目标：重构为 **5 个顶层模块 tab**，把邻近内容聚合、消除近名与决策点超载，保留原有业务行为与无障碍能力。

## 2. 新结构

顶层 5 tab：

| key | label | 来源 |
|-----|-------|------|
| `basic` | 基本信息 | 原 `basic` |
| `casefile` | 案情及当事人材料 | 原 `parties` + `requests` + `materials` |
| `evidence` | 证据和质证 | 原 `evidence`（原样保留） |
| `award` | 仲裁文书 | 原 `signature` + `review` |
| `archive` | 电子卷宗 | 新增占位 |

`activeTab` 类型改为：`'basic' | 'casefile' | 'evidence' | 'award' | 'archive'`。沿用现有 tablist ARIA 键盘导航（左右键 + `aria-selected` + `aria-controls` + scrollTo 居中），仅条目数 7→5。

## 3. 各模块构成

### 3.1 基本信息 `basic`（已去待办）
- 品牌蓝 banner：案号 + 案由（保留现有）
- 案件要点：立案日期 / 组庭日期 / 案件审限 / 争议标的 / 仲裁庭
- 办案秘书：姓名 / 联系电话 / 联系邮箱（现有 mock 若无电话/邮箱则补字段；电话/邮箱做成可点击拨号/发信）
- AI 摘要：保留既有区块

> 待办情况**移除**（用户已确认）。待办驱动的行为入口由 `award` tab 内的未签/待核阅提示承接（见 §4-④）。

### 3.2 案情及当事人材料 `casefile`（长滚 + 模块可折叠）
组织方式：单列长滚，各模块有明确标题分隔；**重模块默认折叠（请求/反请求），当事人核心信息默认展开**。

- **当事人模块**
  - 申请人与申请人代理人、被申请人与被申请人代理人。
  - 默认展示：身份类型（自然人/企业）+ 名字。
  - 用户点击名字后展开该当事人具体信息（ID/名称/住所/联系方式等）。
  - 展开策略：申请人/被申请人两家主当事人默认展开核心身份，仅代理人默认收起。
- **请求和答辩模块**
  - 仲裁条款约定情况 及附件
  - 合同签订主体及签章情况 及附件
  - 事实和理由及仲裁申请书附件
  - 请求类型（多条请求列表）
  - 答辩意见（可多条；每条含：答辩人 / 答辩意见 / 答辩附件）
- **反请求和答辩模块**
  - 反请求事实和理由及反请求申请书附件
  - 反请求类型（多条反请求列表）
  - 反请求答辩意见（可多条；每条含：答辩人 / 答辩意见 / 答辩附件）
- **其他附件**：兜底模块，可空态。

**材料归属**：原「主要材料」tab 的 PDF 拆分挂到对应段落（仲裁申请书→事实和理由；答辩状→答辩附件；合作协议/签章页→合同签订签章段），不再保留集中列表；无法归位的进「其他附件」。

### 3.3 证据和质证 `evidence`
原样搬入，不改结构。沿用现有证据清单、目录折叠、附件胶囊、质证详情。

### 3.4 仲裁文书 `award`（合并）
- 上部：裁决书核阅区（原 `review`：文书内容 + 驳回等）。
- 下部：文书签名区（原 `signature`：庭审笔录、已签/待签裁决书，含 P0 二次确认的签署弹窗）。
- 保留待办「去签名 / 进入核阅」的跳转与降级逻辑（P1 已接通）。
- 未签裁决书/待核阅的提示（红点/徽章）在此 tab 呈现，承接被移除的待办入口。

### 3.5 电子卷宗 `archive`
占位空态，文案「后续实现」。

## 4. 实现约束（源自 impeccable 评审吸收）

- **① casefile 反超载**：重模块默认折叠，口袋能一眼看到「N 项请求 / N 份答辩」计数；避免为找某项盲翻长滚。
- **② 当事人渐进呈现**：默认展开申请人/被申请人核心身份，仅代理人默认收起。
- **③ 语义色单一映射**：**取消请求/反请求的独立 accent 色**（indigo/amber 交由附件/链接），同屏只保留 `申请人=emerald / 被申请人=red` 的当事人语义。DESIGN.md 需补一句明确映射。
- **④ 待办替代入口**：award 内未签/待核阅红点徽章，避免漏掉待办。
- **⑤ 硬编码收敛**：沿用首轮已修复项；本案涉及处（附件胶囊 chip、删除热区）经规范化后不得回退；办案秘书电话/邮箱可点击。

## 5. 备份策略

用 Shell 将当前 `src/components/CaseDetail.tsx` 复制为 `src/components/CaseDetail2.tsx`（存档）。`App.tsx` 保持引用新版 `CaseDetail`，不切换 import。

## 6. 范围与验收

- 不改动数据模型类型定义（仅在 CaseDetail 内调整布置与 const 数据组织）。
- 不改动 `evidence` 的行为与视觉。
- 保留 P0（签名二次确认）、P1（跳转回调/降级）已实现能力。
- 验收：`npm run lint` 零错误；桌面 1280 + 移动 400 两档渲染正常；5-tab 键盘导航通过。

## 7. 技术要点

- 将原 `parties` + `requests/materials` 拆出的可折叠模块抽为组件，减少单文件膨胀。
- 请求/答辩、反请求/答辩沿用现有 const 数组结构（组件内定义），重组映射到 casefile。
- 待办 `caseTodos` 数据可保留但不在 `basic` 渲染。
